## How much detail? (Recommendation)

Use a **three-layer** structure. Most examiners want the *idea* and *primary metric* in Methods; the control-loop mechanics in an appendix.

| Layer | Where | Length | What belongs here |
|-------|--------|--------|-------------------|
| **A — Main Methods** | §4.5 Benchmark | **1–1.5 pages** | Why adaptive load; definition of goodput; SLA rules in plain language; which profile you used; how iteration score is derived |
| **B — Optional subsection** | §4.5.1 Load controller | **½ page** | Step structure (warm-up → ramp → plateau stop); overload/backoff triggers; one figure (adaptive ramp plot) |

## Layer A — Must-have content (main Methods)

### 1. Workload source

- HTTP traffic is generated by **distributed Locust** using BaxBench scenario task definitions (same API surface as functional tests).
- Each virtual user issues requests with a think-time between `wait_min_s` and `wait_max_s` (default 1 s for k8s profiles).
- Load generators run on dedicated hosts, separate from application pods.

### 2. Why not fixed RPS?

Fixed user count or fixed RPS requires per-application tuning and does not find the **capacity knee** automatically.

We use an **adaptive load shape** that:

1. Holds a user level until measurements stabilize.
2. Increases load while the system stays healthy.
3. Backs off on overload.
4. **Stops** when marginal goodput gains flatten (plateau).

This makes iteration scores comparable across different apps and deployment sizes without hand-picking RPS per scenario.

### 3. Primary objective: goodput

Define explicitly:

> **Goodput** = sustained rate of **successful** HTTP responses (requests per second excluding failures).

Raw throughput with high error rates is **not** a win — aligned with what the refinement agent is told in spec/code prompts.

### 4. Profile used in experiments

State clearly which named profile you ran (from `scripts/bench_k8s.sh`):

**`k8s-goodput-plateau`** — the default for k8s iterative benchmarks in this project.

One-sentence summary:

> The controller ramps virtual users in steps, measures per-step goodput and p95 latency, increases load while marginal efficiency is high, and stops after several consecutive steps with \<5% relative goodput growth.

### 5. SLA / overload rules (plain language)

For `k8s-goodput-plateau`, a load step is treated as **overloaded** if **any** of:

| Signal | Threshold (default) |
|--------|---------------------|
| Step failure rate | \> 2% |
| p95 latency | \> 1000 ms |
| Goodput collapse | \< 90% of best goodput seen so far |

On overload: back off users (undo last ramp, with optional queue drain time).

A step is **acceptable** for ramp-up if none of the above trigger and p95 is stable (spread across samples ≤ 5%).

### 6. How the iteration score is computed

Important for reproducibility — two related numbers:

| Metric | Meaning | Used for |
|--------|---------|----------|
| **Peak step goodput** | Max `step_goodput` logged at phase boundaries during the ramp | Adaptive ramp plots, experiment summary table |
| **Sustained goodput** | Best rolling-window mean goodput (30 s) with flat users, fail% ≤ threshold, stable goodput | `goodput_per_iteration` plots, cross-iteration comparison |

State which one is your **primary evaluation metric** in Results (recommend: **sustained goodput** for fair comparison; peak as secondary).

Parameters for sustained scoring are read from the bench `config.json` / load profile (`failure_threshold_pct`, `stability_drift_threshold_pct`).

### 7. Run ceiling

- `run_time_s = 420` (7 min max per bench) for `k8s-goodput-plateau`.
- `max_users = 10_000` ceiling.
- Stop reasons logged: `goodput-plateau`, `max-users-reached`, `goodput-floor`, `run-time-elapsed`, etc.

## Layer B — Optional detail (subsection)

### Step lifecycle (one paragraph + figure)

```text
warm-up (30 s at start_users)
  → for each level:
       spawn / hold users
       trim (15 s) — ignore spawn transients
       sample p95 + interval goodput every 1 s
       wait until stable OR max 40 s per level
       decide: ramp up / back off / stop (plateau)
```

**Figure to include:** your `05-bench/plots/adaptive_ramp.png` from a representative iteration — users, goodput, p95 over time. Caption explains warm-up, a ramp step, and plateau stop.

### Ramp-up logic (conceptual, not code)

- First passing step after warm-up: large initial jump (`max_step_users`).
- Later steps: compute **marginal goodput efficiency**  
  \(\Delta \text{goodput} / \Delta \text{users}\) between consecutive levels.
- High efficiency → multiply step size by `step_up_gain` (1.2×).
- Low efficiency → shrink step (~ efficiency³).
- Negative efficiency → undo last step, explore with minimum step.

### Warm-up and stability (why they matter)

- **Warm-up:** JIT, cold caches, connection pools must not poison the first decision.
- **Stability gate:** step ends only when p95 samples in the decision window have ≤5% spread — avoids deciding while latency is still trending.

## Layer C — Appendix material

### Full parameter table (`k8s-goodput-plateau`)

| Parameter | Value | Role |
|-----------|-------|------|
| `start_users` | 100 | Initial load after warm-up |
| `max_users` | 10_000 | Hard ceiling |
| `min_step_users` / `max_step_users` | 10 / 400 | Ramp step bounds |
| `step_up_gain` | 1.2 | Aggressive growth when efficient |
| `failure_threshold_pct` | 2.0 | Max acceptable fail% per step |
| `collapse_threshold_pct` | 10.0 | Goodput drop vs. best → overload |
| `overload_p95_ms` | 1000 | Latency overload threshold |
| `warmup_step_duration_s` | 30 | Discarded measurements |
| `min_step_duration_s` / `max_step_duration_s` | 20 / 40 | Per-level time bounds |
| `trim_s` | 15 | Ignore measurements right after user change |
| `sample_every_s` | 1 | Sampling interval |
| `min_settle_samples` | 10 | Samples required before decision (~10s at 1s sampling) |
| `quantile` | 0.95 | Latency percentile tracked |
| `stability_drift_threshold_pct` | 5.0 | p95 spread gate |
| `plateau_stop_steps` | 3 | Consecutive flat steps → stop |
| `plateau_goodput_threshold_pct` | 5.0 | “Flat” = \<5% growth |
| `drain_time_s` | 30 | Extra wait after backoff |
| `spawn_rate` | 200 | User spawn rate cap |
| `locust_processes` | 32 | Processes per load host |
| `run_time_s` | 420 | Max bench duration |

## Example prose snippet (Layer A)

> Performance of each deployment is evaluated with distributed Locust using an
> adaptive load profile (\texttt{k8s-goodput-plateau}). Rather than fixing the
> request rate a priori, the controller increases the number of concurrent virtual
> users in steps until the measured **goodput}—successful responses per
> second—stops growing meaningfully. A step is considered overloaded if the
> failure rate exceeds 2\%, p95 latency exceeds 1000\,ms, or goodput drops more
> than 10\% below the best value observed in the run; the controller then reduces
> load and waits for in-flight requests to drain before continuing. Each benchmark
> begins with a 30\,s warm-up period whose measurements are excluded from
> control decisions. We report the maximum **sustained goodput} over a 30\,s
> window with stable user count, failure rate, and goodput variance; this score
> is comparable across refinement iterations and scenarios without per-app RPS tuning.
