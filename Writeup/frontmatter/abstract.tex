\chapter*{Abstract}

\textsc{BaxBench} demonstrates that LLMs can generate complete backend
applications without solving functional
correctness~\cite{vero2025baxbench}. Correctness measured in an isolated single
container is necessary for production use but not sufficient. Deployed backends
run under shared cluster resources, where replica counts, resource limits, and
database topology jointly determine achievable throughput. This thesis asks
whether an LLM agent can close that gap itself: iteratively optimise a deployed
backend service on Kubernetes to maximise sustained goodput, the rate of
successful requests it holds stably.

We extend \textsc{BaxBench} with \textsc{IterBench}, a Kubernetes-based
benchmarking framework whose agent picks one refinement lever per iteration,
revising either the application code or a declarative deployment specification
that a validator checks against a fixed cluster budget. Each
deploy-and-benchmark cycle returns load-test results and cluster-resource
diagnostics to the agent. An adaptive load profile locates each deployment's
sustained-goodput ceiling from rolling load-test statistics, across capacities
two orders of magnitude apart, in bounded time.

We evaluate three models (Claude Opus 4.8, GPT-5.5, GLM-5.2) across seven
\textsc{BaxBench} scenarios and three application frameworks: 63 tasks, each
with ten refinement iterations. Of these, 30 start with zero goodput; 28
recover. Among the 61 tasks that ever serve, 58 improve on their first working
measurement, by a geometric mean of $2.7\times$. GPT-5.5 more than doubles the
geometric-mean best goodput of either other model, while GLM-5.2 matches Claude
Opus 4.8 at a fifth of the cost. Code refinement, the most failure-prone and
most expensive lever, produces the largest single-step gains and a higher mean
effect for every model, its largest jumps fixing correctness or
connection-handling defects exposed under load. Deployment refinement fails
less often, yet the steps that do complete collapse working deployments to zero
goodput more often. Framework choice sets a sustained-goodput cap that
refinement does not lift, and \textsc{Go-net-http}'s is the highest for every
model. LLM-driven optimisation therefore improves deployed services
substantially, but code correctness, more than deployment reasoning, governs
whether a service becomes tunable.
