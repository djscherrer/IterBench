\chapter{Conclusion}
\label{ch:conclusion}


% ----- §7.1 Thesis Summary -----
\section{Thesis Summary}
\label{sec:conclusion-summary}

\textsc{BaxBench}~\cite{vero2025baxbench} and similar benchmarks established
that LLMs can generate functionally correct backend applications, but they
evaluate every candidate in an isolated, single-machine Docker container
and stop at functional and security correctness
(Section~\ref{sec:intro-context}). Nothing in that evaluation methodology
says anything about whether the generated application would serve
production traffic well once it is actually deployed: replica counts,
resource requests, pod placement, and database topology are all decided
outside the scope of the benchmark, by a human operator or a reactive
autoscaler that reasons about none of it jointly
(Section~\ref{sec:intro-gap}). This thesis asked whether an LLM agent
could close that gap itself: iteratively optimise the deployment
configuration of a backend application on a Kubernetes cluster, guided by
runtime performance feedback, to maximise sustainable throughput under
fixed infrastructure constraints (Section~\ref{sec:intro-missing}).

The approach is an iterative benchmarking framework that extends
\textsc{BaxBench} with a real multi-node Kubernetes cluster and a
five-stage refinement loop (decision, code, spec, deploy, bench;
Chapter~\ref{ch:methods}), in which an LLM agent proposes exactly one
change per iteration, to either application code or a constrained
deployment specification (\texttt{spec.yaml}), and receives structured
load-test and resource-utilisation feedback before the next iteration.
Performance is scored by \emph{sustained goodput} under an adaptive load
profile that discovers each deployment's sustainable throughput without
per-scenario rate tuning (Section~\ref{sec:methods-load-profile}). The
methodological contributions this required, a schema that bounds the
agent's deployment search space to meaningful decisions rather than raw
Kubernetes YAML, a failure taxonomy and routing scheme that keeps a
single bad iteration from silently corrupting the next one
(Section~\ref{sec:methods-failure}), and an evaluation harness that
tracks LLM cost as a first-class quantity alongside goodput
(Section~\ref{sec:methods-workflow}), are what make the empirical results
in Chapter~\ref{ch:results} attributable to specific causes rather than an
unexplained end-to-end number.


% ----- §7.2 Key Findings -----
\section{Key Findings}
\label{sec:conclusion-findings}

\paragraph{What worked.} Iterative refinement improved sustained goodput
in essentially every cell with data, across all three evaluated models,
and in a substantial fraction of cells it did not just improve an
already-working deployment but converted a non-functional one into a
functional one (Section~\ref{sec:results-rq1}). Where a trajectory ran
long enough, the agent's deployment-specification choices tracked the
workload's actual scaling characteristics, favouring horizontal fan-out
over per-pod headroom for a near-stateless workload without ever being
told that heuristic, and two different models converged on the same
qualitative decision on the same scenario
(Section~\ref{sec:results-rq6}). Keeping code and deployment refinement
mutually exclusive per iteration turned out to be more than a bookkeeping
convenience: the two levers measurably specialise in practice, with code
refinement carrying almost all of the largest single-step recoveries and
deployment refinement acting as a smaller, more model-dependent capacity
adjustment (Section~\ref{sec:results-rq3}).

\paragraph{What did not work.} Deployment refinement, taken on its own,
was occasionally counterproductive: a well-reasoned response to correct
diagnostics regressed a healthy deployment to zero goodput, because
nothing prevents one refinement step from changing several
deployment-spec fields whose interaction it cannot fully anticipate
(Section~\ref{sec:results-rq7}). For one model, \texttt{glm-5.2}, this was
not a one-off: its deployment-refinement steps are net negative on average
across 66 steps, the only one of the three models where this lever is a
net liability rather than a net gain (Section~\ref{sec:results-rq3}). A
second, more severe instance of the same failure mode shows up on
\texttt{claude-opus-4-8}: one cell starts from a healthy baseline, peaks at
$3\times$ that baseline, and then loses everything again to two
consecutive deployment-refinement regressions with no iterations left in
its budget to recover (Section~\ref{sec:results-rq1}), so the same
occasional-backfire pattern is not confined to the one model whose average
is net negative. Separately, and closer to a framework finding than a
model one: static spec validation did not catch every deployment that
would later prove impossible to schedule, and the taxonomy that records
those failures uses inconsistent labels for what reads as the same
underlying symptom, and is blind entirely to a trajectory that ends at
zero goodput without a single harness-level failure along the way
(Section~\ref{sec:results-rq7}).

\paragraph{What surprised us.} The multiplicative gain from refinement
turned out to depend much more on how badly under-provisioned the
baseline happened to be than on any consistent ``value added by
refinement'' figure: the same framework produced gains ranging from just
over $1\times$ to more than $75\times$ depending on the cell, and the two
largest gains in the dataset landed on the same scenario for two different
models (Section~\ref{sec:results-rq1}). A second surprise was in the
failure taxonomy rather than in goodput: every recorded
\texttt{docker\_build} failure in this dataset, all 14 of them, is a
\textsc{Rust-Actix} compile failure, twelve of them \texttt{glm-5.2}'s
across six different scenarios (Section~\ref{sec:results-rq7}), a
concentrated, framework-specific correctness signal that a
single-container, single-framework evaluation would not surface as
clearly. Also unexpected, though smaller: the deployment-and-cluster path
was \emph{nearly}, but not quite, invisible as a source of failure. A
handful of spec-refinement iterations, across cells from two different
models, produced deployments that passed static validation but could not
be deployed as intended, recorded under two different failure-kind labels
for what reads as the same underlying symptom, and a third instance of the
same label turned out on inspection to be a different root cause entirely,
an application crash loop rather than a scheduling shortfall
(Section~\ref{sec:results-rq7}); the same static validation is also
documented, on two separate cells, correctly rejecting an infeasible
proposal before it was ever applied.

\paragraph{What we learned from the evaluation.} The single biggest
determinant of final performance in this dataset was not deployment
tuning at all, but whether the generated code was correct enough to
survive real load in the first place, including failure modes (a
connection pooler's transaction-mode incompatibility with server-side
prepared statements) that a single-container functional-test suite
structurally cannot observe (Section~\ref{sec:results-rq7}). Evaluating a
deployment-optimisation agent in isolation from code correctness would
have missed this; the two are entangled in practice, even though the
framework deliberately separates them as levers.


% ----- §7.3 Research Question: Final Answer -----
\section{Research Question: Final Answer}
\label{sec:conclusion-rq}

Restating the thesis's central question (Section~\ref{sec:intro-missing}):
\emph{can an LLM agent iteratively optimise the deployment configuration
of a backend application on a Kubernetes cluster, guided by runtime
performance feedback, to maximise sustainable throughput under fixed
infrastructure constraints?}

\textbf{Yes, within the scope this thesis tested.} Across all 63
scenario$\times$framework$\times$model cells in the evaluated matrix,
across three models, an LLM agent that alternates between code and
deployment-specification
refinement, guided only by adaptive load-test feedback and resource
diagnostics, consistently increased sustained goodput once a functionally
correct baseline existed, and in a majority of dead-baseline cells it
produced a working deployment where none existed initially. The
deployment-specification lever specifically, the part of the question
closest to this thesis's actual contribution, since code-level LLM
optimisation is comparatively well studied
(Section~\ref{sec:rw-llm-perf}), behaved as a genuine, if bounded and
model-dependent, optimisation signal: spec trajectories moved toward
workload-appropriate configurations without being given target ranges
(Section~\ref{sec:results-rq6}), and static validation plus the
framework's failure routing kept bad deployment decisions from silently
compounding in most, though not all, observed cases
(Section~\ref{sec:results-rq7}).

The qualification matters as much as the answer. What this thesis cannot
yet say is whether the result generalises beyond seven database-backed
scenarios, one cluster topology, and a ten-iteration budget at $n=1$
sample per cell
(Section~\ref{sec:conclusion-limitations}); nor can it cleanly separate
``the agent optimises deployment configuration well'' from ``the agent
optimises deployment configuration well \emph{once code correctness stops
being the bottleneck}'', in this dataset, the two were rarely
simultaneously true early in a trajectory.


% ----- §7.4 Limitations -----
\section{Limitations}
\label{sec:conclusion-limitations}

The full discussion is in Section~\ref{sec:discussion-limitations}; in
summary, every result in this thesis should be read against: scenario
coverage limited to 7 of \textsc{BaxBench}'s 28 scenarios, all
database-backed, and chosen to span workload shapes rather than to be a
statistically representative sample; a fixed 10-iteration refinement
budget, which this dataset shows can end a trajectory at zero goodput
purely because it runs out before a late regression is corrected; $n=1$
sample per cell, so no comparative claim here has been tested against
sampling variance; overlap between scenario generation and model evaluation
which is checked in Section~\ref{sec:results-rq4} but does not make generated
and original scenarios interchangeable; a subset of load runs using the
lower-bandwidth control network rather than the experiment LAN; a hard
$100{,}000$-user ceiling reached by 31 of the 582 warm-up survivors, which
right-censors that tail of the capacity search; a single scalar (sustained
goodput under one adaptive load profile) as the sole optimisation signal,
which does not distinguish a dead baseline from a trajectory that recovered
and later collapsed again; temperature-$0.2$ but still stochastic LLM
behaviour with no repeated draws to quantify it; and a single cluster
topology and hardware profile, so ``fixed infrastructure constraints'' in
this thesis means one specific capacity envelope, not infrastructure
constraints in general.


% ----- §7.5 Future Work -----
\section{Future Work}
\label{sec:conclusion-future-work}

\paragraph{Steer scenario generation toward diverse, complex bottlenecks.}
Every scenario evaluated here is, structurally, a CRUD application over a
single relational database: read/write operations on rows, with the
deployment-tuning problem consequently concentrated in database topology,
connection pooling, and horizontal fan-out
(Section~\ref{sec:discussion-limitations}). This is a property of the
scenario-construction pipeline (Section~\ref{sec:methods-scenario-gen})
as much as of the workload domain: nothing in it currently steers idea
generation toward a particular bottleneck shape, so it converges on the
same CRUD-over-Postgres pattern scenario after scenario. Extending it to
explicitly target other bottleneck classes, compute-bound work
(image or data processing), memory-bound state (large in-process caches
or aggregations), or coordination-bound work (locking, queues,
multi-step transactions spanning several requests), would test whether
the code/deployment division of labour observed here
(Section~\ref{sec:results-rq3}) is a general property of the two levers or
an artefact of the scenario shapes chosen. The same generation pipeline
could also be pushed toward larger, less crude application shapes, more
resources and relationships per scenario, and multi-step business
processes rather than single-entity CRUD, independently of which
bottleneck class it targets.

\paragraph{Reintroduce security testing.} \textsc{BaxBench} scores
generated code on functional \emph{and} security correctness
(Section~\ref{sec:intro-context}), but this thesis's evaluation carries
forward only the functional side: exploit-style security tests are part
of the inherited scenario format but play no role in the deployment-loop
scoring or the results reported here. Wiring a security-test pass back
into the refinement loop, and tracking whether either refinement lever
introduces or fixes a vulnerability as a side effect of a goodput-motivated
change, would close a gap this thesis's own framing (a benchmark that
should evaluate more than BaxBench's original single-container
functional-and-security check) otherwise leaves open.

\paragraph{Strengthen spec validation and functional-test depth.} Two
separate validation surfaces could plausibly be doing more than they do
now. Static spec validation (Section~\ref{sec:methods-spec}) currently
checks a fixed set of structural and capacity properties; RQ7's
\texttt{unschedulable}/\texttt{namespace\_cleanup} gap
(Section~\ref{sec:results-rq7}) shows at least one class of deployment
failure it does not catch, and it is not obvious that the current check
set is complete rather than simply the set that was implemented first.
Separately, functional-test generation (Section~\ref{sec:methods-code})
could be pushed from today's single-behaviour checks (change one thing,
assert the resulting state) toward layered coverage: keep the small,
cheap per-endpoint checks as a first tier, but add larger scripted user
flows that chain several endpoints together and assert on the
end-to-end outcome, closer to how the load-test scripts already exercise
the API but oriented at correctness rather than throughput. Both would
raise the bar an implementation has to clear before it is trusted, at the
cost of a stricter, more expensive generation pipeline.

\paragraph{Constrain or measure within-lever attribution.} The backfire
case in Section~\ref{sec:results-rq7} shows that a single spec-refinement
step can change several fields at once, which limits attribution the same
way mixing code and spec changes would. Future work could either constrain
spec-refinement steps to one field at a time and measure whether that
improves reliability, particularly for \texttt{glm-5.2}, whose
spec-refinement mean is net negative in this dataset, or instrument enough
to attribute outcomes to individual fields \emph{post hoc} without
constraining the agent's search space.

\paragraph{Protect against a trajectory ending on a regression.} This
dataset now contains one cell that starts from a healthy baseline, peaks
well above it, and then loses everything to two consecutive late
regressions with no budget left to recover (Section~\ref{sec:results-rq1}).
A cheap mitigation worth testing is reporting, or even deploying, the best
validated iteration rather than the last one when a trajectory's budget
runs out mid-regression; a more involved one is letting the decision stage
revert to a known-good spec once a regression is detected rather than
always moving forward. Either would change how often a fixed budget is
the reason a good result is lost rather than a stable measure of it.

\paragraph{Investigate the \textsc{Rust-Actix} build-failure concentration.}
Every \texttt{docker\_build} failure recorded in this dataset is a
\textsc{Rust-Actix} compile failure (Section~\ref{sec:results-rq7}), most
of them \texttt{glm-5.2}'s. Whether this reflects the model's Rust
proficiency specifically, an interaction with this scenario suite's API
shapes, or something about the build toolchain itself is not yet
separable from this dataset alone.

\paragraph{Widen the deployment specification and test transfer across
cluster topology and scale.} All results come from one cluster profile
and one deployment-component vocabulary, backend, database, pooler,
cache (Section~\ref{sec:setup-infrastructure},
Section~\ref{sec:methods-spec}). Two extensions are natural here, and
largely independent of each other. First, growing the
\texttt{spec.yaml} schema to cover more component types, message queues,
background workers, additional cache tiers, would let the agent's search
space match a larger slice of real deployment topologies rather than the
database-and-pooler-centric one evaluated here. Second, repeating even a
subset of cells on a cluster an order of magnitude larger or smaller, or
with a different node/network topology, would show whether the
deployment decisions the agent converges to (Section~\ref{sec:results-rq6})
are tuned to the workload or partly to this specific cluster's capacity
envelope.

\paragraph{Exercise load profiles this evaluation never used.} Every
result here comes from a single adaptive load profile,
\texttt{k8s-explore-refine}, chosen to discover sustainable throughput
without per-scenario tuning (Section~\ref{sec:methods-load-profile}).
Nothing about the agent or the framework is specific to that profile:
running the same refinement loop under a spike or surge profile, sudden,
short-lived traffic bursts well above the sustained rate, rather than a
gradually ramping one, would test a different and arguably more realistic
production concern than steady-state capacity, and would show whether the
deployment decisions favoured for sustained goodput (Section~\ref{sec:results-rq6})
still hold up, or trade away, burst headroom. No such profile exists in
this framework yet; building one is a prerequisite for this direction,
not just a configuration change.

\paragraph{Richer feedback and multi-objective scoring.} Sustained
goodput is deliberately a single number
(Section~\ref{sec:methods-load-profile}); resource-utilisation and
per-endpoint latency diagnostics are already collected
(Section~\ref{sec:methods-outcome}) but not scored. Feeding
cost-per-request or tail-latency objectives into the decision stage
alongside goodput, rather than only into the human-readable feedback, is
a natural extension once repeated sampling puts the single-objective case
on firmer statistical footing.
