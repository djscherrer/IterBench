% ----- §1.1  Broad context: LLMs generating code -----
\section{LLM-Based Code Generation}
\label{sec:intro-context}

Large language models have advanced from completing individual
functions~\cite{chen2021humaneval} to resolving repository-level software
engineering issues~\cite{jimenez2024swebench}, and can now produce complete
backend applications spanning frameworks, databases, and authentication
layers. \textsc{BaxBench}~\cite{vero2025baxbench}, the benchmark this thesis
extends, evaluates that capability at the application level: given a fixed
backend task, it checks whether the generated application is functionally
correct and free of known exploitable vulnerabilities
(Section~\ref{sec:background-codegen}). Across its full suite, even the
strongest models reach only around 62\% functional correctness, and roughly
half of the implementations that pass functional testing remain exploitable.
These results establish that complete-application generation remains difficult,
but they say nothing about how a passing application behaves once it is
deployed and put under load.

\textsc{BaxBench} executes each generated application in an isolated,
single-machine container and measures whether it passes functional and
security tests. That is an appropriate environment for a code-level benchmark,
but it does not assess how the application performs under realistic deployment
conditions.


% ----- §1.2  Narrow the gap: performance under deployment -----
\section{Beyond Correctness: Performance Under Real Deployment}
\label{sec:intro-gap}

In production, backend applications do not run in isolation. They are
deployed on container orchestration platforms such as
Kubernetes~\cite{burns2016borg,kubernetes} (Chapter~\ref{ch:background}
introduces the relevant concepts), where multiple replicas share finite CPU,
memory, and network resources across a cluster of worker nodes. Achieving
high throughput under these conditions requires careful \emph{deployment
configuration}: decisions about replica counts, resource allocation, pod
placement, and database topology
(Section~\ref{sec:background-deployment-levers}).

A functionally correct application can still fail to serve production traffic
if these parameters are poorly chosen. A database bottleneck, an unsuitable
connection pool, too few replicas, or an unfortunate placement decision can
all appear only when requests overlap and compete for shared resources.

Generating correct code is therefore necessary but insufficient for production
readiness. Deployment configuration is an additional optimisation target, but
it is not independent of code correctness: a latent application bug and a
deployment bottleneck can produce similar symptoms under load.

Evaluating this problem therefore requires more than executing an application
in an isolated container. Candidates must be observed on a multi-node
Kubernetes cluster, where replica placement, shared resource capacity, and
database topology can affect the performance that the benchmark measures.


% ----- §1.3  The gap stated explicitly -----
\section{The Research Gap: Deployment Optimisation as an Unexamined Dimension}
\label{sec:intro-missing}

Prior work approaches this boundary from several directions: code- and
system-level performance optimisation, LLM-generated infrastructure, and
learned cluster-management policies. As discussed in
Chapter~\ref{ch:related-work}, these lines differ in what the agent controls,
what feedback it receives, and whether the outcome is deployability or measured
service performance. To our knowledge, no existing benchmark combines an
LLM-controlled application, an LLM-controlled deployment specification, and a
runtime performance objective in one iterative loop on a real multi-node
Kubernetes cluster.

This gap leaves a fundamental question unanswered:
%
\begin{quote}
  \emph{Can an LLM agent iteratively optimise the deployment configuration of
  a backend application on a Kubernetes cluster, guided by runtime performance
  feedback, to maximise sustainable throughput under fixed infrastructure
  constraints?}
\end{quote}


% ----- §1.4  This work -----
\section{This Work}
\label{sec:intro-thiswork}

In this thesis, we present \textsc{IterBench}, a Kubernetes-based iterative
benchmarking framework that extends \textsc{BaxBench} to address this
question.  Given a \textsc{BaxBench} scenario and a target Kubernetes cluster,
\textsc{IterBench} orchestrates a multi-phase refinement loop:
%
\begin{enumerate}
  \item A \textbf{baseline phase} in which the LLM agent generates both
        application code and an initial deployment specification, which are
        validated, deployed, and benchmarked under adaptive load.
  \item An \textbf{iterative refinement phase} in which the agent receives
        structured performance feedback, load-test statistics, per-endpoint
        latency distributions, resource utilisation diagnostics, and the
        previous deployment's goodput, and decides whether to improve the
        application code \emph{or} the deployment configuration, exclusively,
        before repeating the deploy--benchmark cycle.
\end{enumerate}
%
The deployment specification is expressed as a constrained YAML schema
(\texttt{spec.yaml}) that gives the agent control over the deployment decisions
introduced in Section~\ref{sec:background-deployment-levers}, including
replication, resource allocation, placement, and data-tier configuration,
while the framework handles manifest rendering, Kubernetes resource
management, and orchestration.

Performance is measured using the adaptive Explore-and-Refine load profile,
which measures each deployment's sustained goodput
(Section~\ref{sec:background-goodput}) directly rather than driving the
system at a fixed request rate. An intelligent load controller increases
concurrent virtual users while observing latency and throughput, exploring
quickly until goodput stops improving or the system becomes unhealthy, then
settling into an accurate, feedback-driven measurement of sustained goodput
near that boundary. The same procedure is then used across applications,
deployment sizes, and refinement rounds. Every LLM call is logged against its
measured cost, so model comparisons can be read alongside capability rather
than in place of it.


% ----- §1.5  Research questions -----
\section{Research Questions}
\label{sec:intro-rqs}

The central question above is broad enough that answering it in aggregate
would hide more than it reveals: whether refinement helps, which lever drives
that help, whether it depends on the model, and where it breaks down are
separate empirical claims. It also rests on a measurement whose own behavior
needs checking before it can carry that weight: every iteration score in this
thesis comes from the Explore-and-Refine load profile
(Section~\ref{sec:methods-load-profile}). Chapter~\ref{ch:results} therefore
validates that measurement instrument first
(Section~\ref{sec:results-load-profile-validation}), then decomposes the
central question into five questions asked of the same dataset (three models,
seven \textsc{BaxBench} scenarios, three frameworks;
Chapter~\ref{ch:setup}):
%
\begin{description}
  \item[RQ1] Does iterative refinement improve sustained goodput, and how
    does that improvement differ across the three models
    (Section~\ref{sec:results-rq1})?
  \item[RQ2] Which refinement lever, code or deployment, contributes more,
    and do the two specialise on different failure classes
    (Section~\ref{sec:results-rq3})?
  \item[RQ3] Does a scenario's static task complexity explain which
    scenarios are harder to optimise, in baseline health, failure rate, and
    headroom left for refinement (Section~\ref{sec:results-rq4})?
  \item[RQ4] Does application-framework choice affect achievable goodput
    independently of refinement (Section~\ref{sec:results-rq5})?
  \item[RQ5] Which failure sources are most prominent in this dataset, and
    how does their frequency compare across phases, models, and tasks
    (Section~\ref{sec:results-rq6})?
\end{description}
%
Scenario and framework each get a question of their own (RQ3, RQ4) because
they are properties of the optimisation problem the agent is handed. The
choice of model is a property of the agent itself, and so cuts across all
five questions rather than forming a sixth: every question above is reported
per model, and the accompanying cost comparison is collected in
Appendix~\ref{ch:appendix-additional-results}.
Chapter~\ref{ch:discussion} interprets the five answers together, and
Chapter~\ref{ch:conclusion} returns to the overarching question directly.


% ----- §1.6  Contributions -----
\section{Contributions}
\label{sec:intro-contributions}

This thesis makes the following contributions:
%
\begin{enumerate}
  \item \textbf{An iterative benchmark framework} (\textsc{IterBench}) that
        extends \textsc{BaxBench} with Kubernetes deployment, adaptive load testing,
        and a multi-phase refinement loop in which the agent chooses between
        code and deployment refinement. Deterministic failure
        routing (Section~\ref{sec:methods-failure}) preserves artifact lineage
        and makes failed iterations attributable to a recorded stage rather
        than an unexplained end-to-end outcome.

  \item \textbf{A constrained deployment specification} (\texttt{spec.yaml})
        that exposes a structured search space for the LLM agent, covering
        replica count, resource requests and limits, database topology, and pod
        placement, while the framework enforces cluster-capacity validation
        and deterministic manifest rendering.

  \item \textbf{An adaptive load profile}
        (\texttt{k8s-\allowbreak explore-\allowbreak refine}) that
        estimates a deployment's sustained goodput without per-application
        rate tuning, ramping load through an
        explore phase to locate an approximate overload boundary, then a
        refine phase that searches near it in efficiency-scaled steps,
        with overload and stall detection based on failure rate, tail
        latency, and goodput collapse thresholds.

  \item \textbf{An experimental evaluation} across three frontier-tier
        LLMs, seven \textsc{BaxBench} scenarios, and three application
        frameworks, covering all 63 scenario--framework--model tasks, while
        tracking LLM cost alongside goodput. The evaluation shows that refinement
        generally improves sustained goodput, that code and deployment changes
        address different failure classes, and that outcomes vary with the
        model and application framework (Chapter~\ref{ch:results}).
\end{enumerate}


% ----- §1.7  Thesis outline -----
\section{Thesis Outline}
\label{sec:intro-outline}

The remainder of this thesis is organised as follows.
%
\begin{description}
  \item[Chapter~\ref{ch:background}] covers \textsc{BaxBench}, Kubernetes,
    deployment levers, and the performance vocabulary used later.

  \item[Chapter~\ref{ch:related-work}] surveys related work on LLM code
    generation and evaluation, iterative self-refinement and agentic coding,
    verification-gated generation, deployment configuration and learned
    cluster management, and LLM-driven performance optimisation, and
    positions this thesis against it.

  \item[Chapter~\ref{ch:methods}] describes the system architecture, the
    iterative experiment loop and its individual phases, the adaptive load
    profile and goodput metric, failure handling, and the constrained
    deployment specification.

  \item[Chapter~\ref{ch:setup}] details the experimental setup, including
    cluster configuration, selected models, scenarios, and hyperparameters.

  \item[Chapter~\ref{ch:results}] presents the evaluation, first validating the
    load-profile measurement instrument and then answering the five research
    questions of Section~\ref{sec:intro-rqs}, before a closing summary
    connects the answers back to the overarching question of
    Section~\ref{sec:intro-missing}.

  \item[Chapter~\ref{ch:discussion}] interprets those results, discusses their
    limitations and threats to validity, and draws out practical implications
    for agentic software optimisation and Kubernetes deployment optimisation.

  \item[Chapter~\ref{ch:conclusion}] answers the overarching research question
    directly, summarises what worked and what did not, and outlines
    directions for future work.
\end{description}
