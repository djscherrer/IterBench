\chapter{Experimental Setup}
\label{ch:setup}

This chapter fixes the concrete instantiation of the framework described in
Chapter~\ref{ch:methods}: which models, scenarios, frameworks, and cluster
were used, and which settings were chosen for the resulting tasks, samples,
experiments, and iterations (Section~\ref{sec:methods-workflow}).
Chapter~\ref{ch:results} assumes this setup and focuses on findings.


% ----- §4.1 Models -----
\section{Models}
\label{sec:setup-models}

Three frontier-tier LLMs were evaluated: \textbf{\texttt{claude-opus-4-8}}
(Anthropic), \textbf{\texttt{gpt-5.5}} (OpenAI, snapshot
\texttt{gpt-5.5-2026-04-23}), and \textbf{\texttt{glm-5.2}} (Z.ai): the
three major provider families available at the time of experimentation.
All three are accessed through the same conversational, cache-aware harness
(Section~\ref{sec:methods-workflow}), with generation configuration held
fixed across models: temperature $0.2$, the \texttt{openapi} spec type, and
the \texttt{high\_performance} safety-prompt variant
(Section~\ref{sec:methods-code}). All three also offer a comparable context
window (Table~\ref{tab:setup-model-config}: approximately $1{,}000{,}000$
tokens each, \texttt{gpt-5.5} marginally larger at $1{,}050{,}000$), so that
dimension is already roughly matched rather than a confound to control for.
What genuinely differs by provider is cost and how each one caches a
growing conversation, and that difference is left in place rather than
unified: it is exactly what lets a model's capability be read alongside
its cost, instead of only in isolation.

\paragraph{Caching policy.} The general prompt-caching mechanism is
described in Section~\ref{sec:methods-memory}; the concrete policy differs
by provider, since each exposes caching differently.

\texttt{claude-opus-4-8} places an explicit cache breakpoint on the system
prompt and on the latest conversation turn, with a 1-hour time-to-live
rather than Anthropic's 5-minute default: a full iteration (Deploy plus
Bench, including the cluster-side load test) routinely runs longer than 5
minutes, which would otherwise evict the cache before the next call could
reuse it. Anthropic prices the initial cache write at a premium that
scales with the chosen TTL ($1.25\times$ input for 5 minutes, $2\times$ for
1 hour). Only the newest turn is written at that premium on any given
call, while the entire accumulated conversation so far is read back from
cache at a $0.1\times$ discount; as a trajectory lengthens, the cheap
read side keeps growing while the premium-priced write side per call
stays roughly constant, so the 1-hour choice is worth its higher upfront
cost once a few iterations have accumulated.

\texttt{gpt-5.5} caches differently: rather than an explicit,
manually placed breakpoint with its own time-to-live, OpenAI detects a
repeated prompt prefix automatically and keeps it available for a
configured retention window (\texttt{prompt\_cache\_retention}, set to 24
hours here) instead of a TTL tied to a specific write. A stable
\texttt{prompt\_cache\_key}, one per experiment sample rather than
anything derived from the prompt content itself, is attached to every
call so that repeated requests from the same trajectory are routed back
to the same cached instance rather than to a different backend that would
have to rebuild the cache from scratch. Because the cache is populated as
a by-product of ordinary request processing rather than an explicit
annotated write, there is no separate write premium: a cache write bills
at the ordinary input rate.

\texttt{glm-5.2}, accessed through OpenRouter rather than a first-party
API, caches implicitly: the upstream provider caches the prompt prefix on
its own, and OpenRouter routes follow-up calls to the same backend
instance so that cache stays useful. The harness does not need to send
any explicit cache parameters for this model.

\paragraph{Why these three.} The selection targets provider diversity at a
comparable capability tier rather than an exhaustive model sweep. This is
mainly for economical reasons: exactly one iterative refinement trajectory
already costs several dollars in LLM spend, so the achievable sweep is
restricted to the low single digits of models, not dozens.


% ----- §4.2 Scenarios -----
\section{Scenarios}
\label{sec:setup-scenarios}

Seven \textsc{BaxBench} scenarios were evaluated, chosen to span a range of
workload shapes. Three of them (\textsc{ClickCount}, \textsc{Recipes},
\textsc{Petstore}) are original \textsc{BaxBench} scenarios; the other four
(\textsc{BranchWeave}, \textsc{ParcelPinLockerPickup},
\textsc{SplitNestSharedExpenseLedger}, \textsc{TransitPulseDelayReporter})
were produced by the scenario-construction pipeline of
Section~\ref{sec:methods-scenario-gen}. This is a subset of the full
\textsc{BaxBench} suite (28 scenarios; Section~\ref{sec:rw-benchmarks}),
not an exhaustive sample of it. All seven require a backing database,
making database topology and connection handling
(Section~\ref{sec:methods-spec}) relevant to every task. They differ
mainly in API surface size and statefulness.

\paragraph{Generation parameters.} For the four generated scenarios,
\texttt{gpt-5.5} drove the pipeline's own reasoning steps (scenario idea,
API specification, and functional-test generation and iteration;
Section~\ref{sec:methods-scenario-gen}), with a difficulty setting of 5
endpoints. \texttt{glm-5.2}, \texttt{gemini-3.6-flash}, and
\texttt{deepseek-v4-flash} supplied the reference implementations used to
calibrate the resulting functional and load tests
(Sections~\ref{sec:methods-scenario-gen-functional}
and~\ref{sec:methods-scenario-gen-locust}); as with every reference
implementation in this thesis, none of the three is itself a candidate in
the later model-evaluation experiments.

This creates a potential \emph{provenance bias}: an evaluated model could
benefit from having authored part of the scenarios or from having supplied a
reference implementation used to calibrate their tests. The setup therefore
does not make the three model comparisons fully provenance-independent, and
this thesis does not isolate that effect; it is discussed as an open
construct-validity caveat in Section~\ref{sec:discussion-limitations}.
Generated and original scenarios do differ in baseline health, failure
profile, and refinement headroom (RQ3, Section~\ref{sec:results-rq4}), for
reasons the data does not attribute to authorship one way or the other.

Endpoint counts below are unique OpenAPI paths, not operations
(\textsc{Petstore}'s 8 paths, for example, carry 13 operations across the
four HTTP methods they use); a compact reference table with the same
counts is given in Appendix~\ref{ch:appendix-config}.

\begin{description}
  \item[\normalfont\textsc{ClickCount}] (2 endpoints, 1 functional test) registers and
    retrieves per-user click counts behind secret-based authentication; it
    is the smallest surface of the seven.
  \item[\normalfont\textsc{Recipes}] (5 endpoints, 1 functional test) lets users
    upload, comment on, and rate recipes, a moderate read/write mix.
  \item[\normalfont\textsc{BranchWeave}] (5 endpoints, 5 functional tests) builds and
    traverses branching narrative graphs, with a deterministic playthrough
    simulation and an HTML export endpoint; its graph-shaped data gives it
    the largest functional-test surface of the seven relative to its
    endpoint count.
  \item[\normalfont\textsc{Petstore}] (8 endpoints, 3 functional tests) manages pets,
    orders, and users and has the largest API surface of the seven.
  \item[\normalfont\textsc{ParcelPinLockerPickup}] (6 endpoints, 4 functional tests)
    registers numbered lockers, deposits parcels against a recipient and
    PIN, and claims them by locker number and PIN, with pickup history
    tracked per locker.
  \item[\normalfont\textsc{SplitNestSharedExpenseLedger}] (6 endpoints, 4 functional
    tests) lets users create or join expense groups, log shared payments
    with per-participant shares, and compute member balances derived from
    those shares.
  \item[\normalfont\textsc{TransitPulseDelayReporter}] (5 endpoints, 3 functional
    tests) lets riders submit transit delay reports per station and route
    and query per-station summaries and their own reports.
\end{description}

Each scenario is combined with up to three application frameworks
(\textsc{Go-net-http}, \textsc{Python-Flask}, \textsc{Rust-Actix}), spanning
a compiled natively-concurrent runtime, an interpreted WSGI stack (the
standard synchronous Python web-server interface, run here under
\texttt{gunicorn}), and a compiled async runtime respectively: three points
on the throughput-ceiling spectrum that Section~\ref{sec:results-rq5} uses
to separate framework effects from refinement effects.


% ----- §4.3 Infrastructure -----
\section{Infrastructure}
\label{sec:setup-infrastructure}

Experiments run on a dedicated 9-host cluster on Emulab, all nine hosts
identical \texttt{d430} nodes (32 CPU cores, approximately 62.7\,GiB of
memory each) allocated from a single experiment topology, following the
architecture described in Section~\ref{sec:methods-architecture}:

\begin{itemize}
  \item \textbf{Control plane / orchestrator / registry (1 host).} For
        operational simplicity, a single node runs the Kubernetes control
        plane, the \textsc{IterBench} orchestrator, and the private image
        registry.
  \item \textbf{Kubernetes workers (4 hosts).} Candidate deployments
        (application pods, databases, poolers, caches) are scheduled only
        onto these nodes, whose four d430 hosts contribute 128 CPU cores
        and approximately 251\,GiB of memory in total. Static validation
        enforces the nodes' \emph{allocatable} capacity, that is, what
        remains after Kubernetes' own system reservations, which is somewhat
        below this raw figure and is read live from the cluster every time a
        deployment specification is generated or validated
        (Section~\ref{sec:methods-spec}) rather than assumed once and cached.
  \item \textbf{Locust load generation (4 hosts).} One host runs the Locust
        master process, collocated with 16 of its own worker processes; the
        remaining three hosts each run 32 worker processes. All four are
        disjoint from the Kubernetes workers, so measured goodput is not
        confounded by load-generation CPU contention
        (Section~\ref{sec:methods-architecture}).
\end{itemize}

\paragraph{Network-path caveat.} The intended high-volume load path uses the
Emulab experiment LAN: the harness resolves the Kubernetes NodePort target
and the distributed Locust addresses to the experiment-network interfaces
rather than sending benchmark traffic over the shared control network. A
subset of earlier archived runs nevertheless used the control-network path
before this routing was made consistent; later runs used the experiment LAN.
Because the two networks do not provide the same bandwidth, this is a
potential measurement confound in the affected runs, independent of the
deliberate CPU separation between load hosts and Kubernetes workers. The
network metadata is retained for the repeatability analysis in
Section~\ref{sec:results-rq2}; its implications for comparability and model-
level claims are discussed in Section~\ref{sec:discussion-limitations}.

This measured allocatable capacity, minus the validation reserves
(Section~\ref{sec:methods-spec}), is exactly what the spec-schema static
validation checks candidate deployments against, and it is fixed for the
whole evaluation, which is what makes ``fixed infrastructure constraints''
in the thesis research question concrete.


% ----- §4.4 Evaluation Procedure -----
\section{Evaluation Procedure}
\label{sec:setup-procedure}

The unit hierarchy (task $\to$ sample $\to$ experiment $\to$ iteration) is
defined in Section~\ref{sec:methods-workflow}; this section states the
concrete budget values used throughout Chapter~\ref{ch:results}.

\begin{itemize}
  \item \textbf{Tasks.} Every combination of the 7 scenarios and 3
        frameworks (Section~\ref{sec:setup-scenarios}), crossed with the 3
        evaluated models (Section~\ref{sec:setup-models}): 63 tasks in
        total.
  \item \textbf{Samples.} One sample per task ($n=1$). This is a budget
        constraint, not a methodological preference: preliminary
        experiments showed roughly \$1--7 per task in LLM spend alone,
        compounded by each experiment's long wall-clock runtime (typically
        2 to 3 hours end to end for the full ten-iteration budget), so
        repeated sampling across the tasks evaluated here was not
        affordable within this thesis's compute budget. Its consequence is
        statistical uncertainty: it provides no repeated draws from which
        within-task variance or significance can be estimated. Model- and
        framework-level aggregates are therefore descriptive summaries of
        this fixed grid, not estimates based on independently sampled tasks.
        The measurement and inference consequences are stated in
        Section~\ref{sec:methods-metrics}, revisited where relevant in
        Chapter~\ref{ch:results}, and consolidated in
        Section~\ref{sec:discussion-limitations}.
  \item \textbf{Experiments.} One experiment per sample, i.e.\ one
        refinement trajectory per task; no re-runs under different
        budgets/profiles were kept for the tasks reported here.
  \item \textbf{Iteration budget.} $N{=}10$ refinement iterations
        (iterations \texttt{000}--\texttt{010}) per experiment, plus up to
        10 baseline generation attempts (Section~\ref{sec:methods-code})
        and 3 retries per LLM call to absorb transient errors in
        communication with the inference provider
        (Appendix~\ref{ch:appendix-config}).
  \item \textbf{Load profile.} \texttt{k8s-explore-refine}
        (Section~\ref{sec:methods-load-profile}) for every bench.
  \item \textbf{Cost tracking.} LLM spend is logged per experiment
        (Section~\ref{sec:methods-workflow}) and reported alongside
        capability in Chapter~\ref{ch:results}.
\end{itemize}
