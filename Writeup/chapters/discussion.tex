% ----- §6.1 Interpretation -----
\section{Interpreting the Results}
\label{sec:discussion-interpretation}

\paragraph{Code correctness decides whether there is a working deployment
to tune at all.} The two levers are not symmetric, and the asymmetry runs
the same way for all three models. Code is where iterations are lost: 47
of the 61 recorded failures fall in the code phase, 45 of them
functional-test or build failures (Section~\ref{sec:results-rq6}), and
code refinement fails outright before producing any measurement in
$14.6\%$ of the steps that choose it, against $4.0\%$ for deployment
refinement (Section~\ref{sec:results-rq3}). Code is also where the
recoveries come from: it revives a dead predecessor more often than
deployment refinement does, and it carries the heavy positive tail of
single-step gains for every model, even where its typical step is not the
larger of the two (Section~\ref{sec:results-rq3}). The asymmetry is
therefore about which lever moves a task \emph{into} a working state, not
about which one is safe to use once it is there. Deployment refinement is
not risk-free once it runs: every model has deployment steps that collapse
a working deployment to zero goodput (Section~\ref{sec:results-rq3}), and
the case studies show one doing so on a well-reasoned rationale
(Section~\ref{sec:results-case-studies}). The claim this data supports is
the narrow one, that code correctness governs the path into a working
state, rather than the broader one that code refinement is the better or
safer lever in general.

\paragraph{The models differ, but that ordering is the weaker of the two
patterns.} \texttt{gpt-5.5} reaches a geometric-mean best goodput more
than double \texttt{claude-opus-4-8}'s (Section~\ref{sec:results-rq1}), so
model choice is plainly not neutral for the outcome. That ranking,
however, rests on one draw per task, whereas the lever asymmetry above
reappears independently in all three models, which makes it the better
supported of the two findings even though the model gap is the more
conspicuous one. The model differences that do appear also sit in a
narrower place than raw completion counts would suggest: all 63 tasks
reached a baseline and completed the full ten-iteration refinement budget
(Chapter~\ref{ch:results}), so the interesting variation in this dataset
is not \emph{whether} a model finishes, but how it uses the two levers
once it starts.

\paragraph{What can and cannot be said about cost.} \texttt{glm-5.2} costs
roughly a fifth as much per task as \texttt{gpt-5.5} or
\texttt{claude-opus-4-8} (Section~\ref{sec:results-cost}),
and that advantage costs it neither completion reliability nor achieved
goodput: it completes every task and its geometric-mean best goodput
slightly exceeds \texttt{claude-opus-4-8}'s
(Section~\ref{sec:results-summary}). Where its profile does look
different is in
how its two refinement levers behave once it is running: its
deployment-refinement steps collapse a working deployment to zero goodput
more often than any other model's do (Section~\ref{sec:results-rq3}), and
its code-side failure profile leans more heavily on \textsc{Rust-Actix}
build failures than the other two models' do (Section~\ref{sec:results-rq6}).
Cost, completion reliability,
achieved goodput, and refinement-lever quality are separate axes in this
data, and \texttt{glm-5.2} only underperforms on the last of them.

\paragraph{Deployment-specification versus code refinement.} The division
of labour in Section~\ref{sec:results-rq3}, code refinement carrying
correctness-adjacent fixes with a heavy positive tail, deployment
refinement acting as a smaller and, for one model, occasionally negative
capacity knob, is consistent with what each lever can structurally see. A
deployment-refinement step can move replicas, resources, and database topology,
but it cannot change what the running application \emph{does}; if the
bottleneck is a connection-handling bug
(Section~\ref{sec:results-case-studies}), no amount of deployment refinement reaches
it. The reverse is not quite symmetric: code refinement \emph{can}, in
principle, work around a deployment problem by changing application
behaviour (for example, reducing per-request work), which may explain why
code refinement's observed effect is not just larger on average but more
variable in both directions than deployment refinement's.

\paragraph{Difficulty is not one quantity, and the framework sets the
ceiling refinement works inside.} The two structural factors this thesis
varied deliberately, scenario and framework, act on different parts of a
trajectory. Scenario difficulty does not reduce to a single number:
static surface size tracks loosely with how often a baseline starts
healthy, but not at all with how much headroom refinement then finds.
\textsc{Petstore} and \textsc{ClickCount} make the point together, since
both start dead more often than the rest of the suite yet sit at opposite
extremes of refinement headroom, the largest API surface leaving almost
nothing to gain and the smallest leaving the most
(Section~\ref{sec:results-rq4}). The practical
consequence for a benchmark of this kind is that a suite selected on
static complexity alone would not control the property that actually
matters for a refinement study, namely how much distance there is between
a naive implementation and its own ceiling. Framework choice acts
differently again: it sets an achievable-goodput ceiling that refinement
operates within rather than around, with \textsc{Go-net-http} highest for
every model (Section~\ref{sec:results-rq5}). That the \emph{lowest}
framework is model-dependent is the weaker of the two findings, since for
\texttt{claude-opus-4-8} it rests on two \textsc{Rust-Actix} tasks that
stall at their first successful iteration rather than on a systematic
language-level effect, exactly the kind of single-draw sensitivity the
$n=1$ design cannot rule out.

\paragraph{Convergence patterns.} Where a trajectory has enough successful
iterations to work with, the \textsc{ClickCount} case study
(Section~\ref{sec:results-case-studies}) shows deployment parameters
moving in a consistent direction across several iterations rather than
oscillating: once the agent identifies that horizontal fan-out beats
per-pod headroom for a near-stateless workload, later deployment-refinement iterations
continue in that direction rather than re-deriving it from scratch, which
is the behaviour the append-only conversational memory of
Section~\ref{sec:methods-workflow} is designed to support. This is one
trajectory, not a general property of the dataset; the backfire case in
the same section, on the very same task, is the counter-example:
convergence toward a \emph{locally} reasonable decision is not the same
as convergence toward a good one, particularly when one refinement step
is free to change several spec fields whose interaction it cannot fully
anticipate.


% ----- §6.2 Limitations -----
\section{Limitations}
\label{sec:discussion-limitations}

The points below are best understood as limitations and threats to validity:
some restrict how broadly the results can be generalised, while others affect
the comparability or interpretation of individual measurements. They do not
invalidate the evaluation, but they delimit the claims that can be made from
it.

\paragraph{Scenario coverage.} Seven of \textsc{BaxBench}'s 28 scenarios
were evaluated (Section~\ref{sec:setup-scenarios}), chosen to span a range
of workload shapes rather than to be a representative sample in a
statistical sense. All seven require a database; none is compute-bound in
the way an image-processing or cryptographic scenario would be, so the
deployment-optimisation story this thesis tells is specifically a
\emph{database-and-network-bound} story. Whether the same code/deployment
division of labour holds for CPU-bound workloads is untested.

\paragraph{Scenario provenance.} Two of the three evaluated models also
took part in building the scenario suite: \texttt{gpt-5.5} served as the
orchestration model for the four generated scenarios, and
\texttt{glm-5.2} supplied one of the three reference implementations their
tests were calibrated against (Section~\ref{sec:setup-scenarios}). This
overlap between artifact author and evaluated candidate is a
construct-validity threat to the model comparison.
The generated and original scenarios are not therefore interchangeable
workloads: their absolute goodput levels differ, and RQ3
(Section~\ref{sec:results-rq4}) shows they also differ in baseline health,
failure profile, and refinement headroom for reasons unrelated to
authorship. This thesis does not isolate the provenance effect itself: doing
so convincingly would need either a provenance-independent fourth model or
repeated draws per scenario, neither of which this single-sample,
three-model design provides. It is recorded here as an acknowledged,
unexamined threat rather than a checked one, bounded by the same
single-sample caveat as every other comparison.

\paragraph{Iteration budget.} Every experiment used a fixed $N{=}10$
refinement budget (Section~\ref{sec:setup-procedure}). Several
trajectories in Chapter~\ref{ch:results} were still improving, or had just
recovered from a regression, at iteration 010; a larger budget could
change both the achieved goodput ceiling and the RQ2 code-vs-spec split,
since which lever a decision stage reaches for next may depend on how many
refinement rounds it has already spent recovering from earlier failures.
This is not only a hypothetical concern: one task in this dataset
(\texttt{claude-opus-4-8}'s \textsc{BranchWeave}$\times$\textsc{Rust-Actix},
Section~\ref{sec:results-rq1}) starts from a healthy baseline, peaks at
$3\times$ that baseline, and then ends its fixed budget at zero goodput
after two consecutive late regressions it never gets a further iteration
to correct. A one- or two-iteration longer budget might well have changed
that task's final outcome without changing anything about the model's
underlying behaviour.

\paragraph{Sample count.} Every task is $n=1$
(Section~\ref{sec:setup-procedure}). A single code-generation seed can be
unusually lucky or unlucky, and Chapter~\ref{ch:results} already flags
several ratios (Section~\ref{sec:results-rq1}) that rest on 7-to-14
healthy-baseline tasks per model. Per-task numbers should therefore be
read as single-draw estimates, not distributions. Model- and
framework-level summaries average over 21 tasks each and so damp the
influence of any one unlucky generation
(Section~\ref{sec:methods-metrics}), but no comparative number here has
been significance-tested against sampling variance, because there is no
repeated-sample data to test it against; the load profile's own
run-to-run measurement variance is a separate axis, quantified in
Section~\ref{sec:results-load-profile-validation} and discussed below.

\paragraph{Benchmark methodology.} Sustained goodput
(Section~\ref{sec:methods-load-profile}) is a single scalar chosen to make
iterations comparable without per-scenario rate tuning. It necessarily
discards information a multi-metric evaluation would keep, tail latency
distribution shape, resource-utilisation efficiency, cost per served
request, some of which is already collected as diagnostics
(Section~\ref{sec:methods-outcome}) but not used as a scoring signal. The
explore/recovery/refine load-profile mechanics
(Section~\ref{sec:methods-load-profile}) also mean that a deployment which
never passes its warm-up health check is scored identically (goodput
$=0$) to one that technically starts but collapses immediately under the
first load step; Section~\ref{sec:results-rq1} treats both as ``dead
baselines'' without distinguishing them further, and the two tasks that
never recover within their ten-iteration budget are recorded the same way
throughout. A goodput of $0$ at the \emph{end} of an otherwise-healthy
trajectory is scored identically again, even though it is a different
phenomenon (Section~\ref{sec:results-rq1}): the failure taxonomy
(Section~\ref{sec:results-rq6}) does not flag it at all, since every
individual iteration still completed as a harness-level success.

\paragraph{Stochastic LLM behaviour.} Temperature was fixed at $0.2$
(Section~\ref{sec:setup-models}), a deliberate reduction of but not an
elimination of run-to-run variance; combined with $n=1$ sampling, this
thesis cannot separate ``this model is worse at this scenario'' from
``this particular draw was unlucky.'' Provider-side model updates between
the writing and the final submission of this thesis are a related, less
controllable source of drift: model snapshots were pinned where providers
exposed a dated snapshot (Section~\ref{sec:setup-models}), but not every
provider does so.

\paragraph{Infrastructure constraints.} All results come from one cluster
topology and one hardware profile (Section~\ref{sec:setup-infrastructure}).
``Fixed infrastructure constraints'' in the thesis research question
(Section~\ref{sec:intro-missing}) is therefore fixed to \emph{one} specific
capacity envelope; whether the same deployment decisions (e.g.\ the
replica-count/CPU-request trade-off of Section~\ref{sec:results-case-studies})
would be reachable, or would be the right decisions, on a cluster an order
of magnitude larger or smaller is untested.

\subsection{Measurement and comparability caveats}
\label{sec:discussion-measurement-caveats}

\paragraph{Measurement noise near the zero threshold.} The load-profile
validation (Section~\ref{sec:results-load-profile-validation}) puts a number
on how much of the reported variation is the instrument rather than the
deployment: re-measuring an unchanged candidate moves the estimate by a
median $2.9\%$, small relative to the effects this chapter interprets, but
with a tail that reaches $15.7\%$ at the 90th percentile. The more
consequential part is where the two measurements disagree on the binary
outcome at all. Those disagreements are concentrated among low-goodput
candidates and split almost evenly in both directions, so the
\emph{serving} versus \emph{dead} classification that Chapter~\ref{ch:results}
relies on for its dead-baseline and collapse counts is least reliable exactly
for deployments sitting close to the edge of failing under load. Aggregate
counts of the form ``$n$ tasks recovered a dead baseline'' should therefore
be read with a tolerance of a few tasks either way, even though the direction
of the effect they describe is far larger than that tolerance.

\paragraph{Network-path comparability.} The load path was not identical for
every archived run at generation time. A subset of the earlier runs used the
shared Emulab control network for part of the Locust--NodePort path, whereas
later runs used the higher-bandwidth experiment LAN intended for sustained
benchmark traffic (Section~\ref{sec:methods-architecture}); a control-network
bottleneck can make a candidate appear to have a lower capacity than it would
on the experiment LAN. To keep the reported goodput comparable across tasks,
every experiment measured before the internal-network cutover was
re-benchmarked on the experiment LAN in a deploy-only re-verification, and its
original control-network measurement replaced with the internal-LAN one. The
results in Chapter~\ref{ch:results} therefore rest on a network-consistent
ground truth in which every goodput number comes from the same load path. One
residual caveat remains: the code and deployment candidates in those tasks
were still \emph{proposed} by the agent under the earlier setup, so it is the
measurement, not the generation, that has been made uniform; a candidate the
agent might have proposed differently under the faster network is not
recoverable after the fact.

\paragraph{User-ceiling censoring.} The load profile has a hard ceiling of
$100{,}000$ virtual users (Section~\ref{sec:methods-load-profile}). The
explore phase reached that ceiling in 44 of the 588 runs that passed warm-up
($7.5\%$; $7.0\%$ of all 632 parsed bench runs), so those runs do not identify
where the deployment would eventually saturate above the ceiling. Their
reported goodput remains a valid observation at the tested load, but the
capacity search is right-censored: a ceiling hit should be read as ``at least
this much offered load was reached,'' not as evidence that the measured value
is the deployment's maximum. Increasing the ceiling, or reporting ceiling
hits separately in every aggregate, would make this tail of the workload
distribution more informative.

\paragraph{Aggregation across the scenario grid.} Aggregating over the
scenario--framework grid is useful as a descriptive summary of the fixed
benchmark suite, and it reduces the visual influence of any one task. It does
not, however, turn the 21 tasks per model into 21 independent draws from a
general workload population: scenarios and frameworks are deliberately
structured, and each task has only one stochastic sample. Model- and
framework-level aggregates should therefore be read as summaries of this
grid, not as population estimates with conventional inferential guarantees.

\paragraph{Concurrent-sweep image caching.} The recurring
\texttt{docker tag failed: ... No such image} error documented in
Section~\ref{sec:results-rq6} traces to a disk-management routine that runs
at the start of every sample's preflight and clears unused container
images from the shared build host, so that a spec-only iteration reusing
an image built earlier in the same task can find it already evicted if
another task's preflight happened to run in between. Because experiments
in this dataset were collected with multiple tasks running concurrently,
this is a genuine race rather than a one-off transient error. Its effect
was contained to the two tasks and iteration pairs Section~\ref{sec:results-rq6}
records: all four abort early in the deploy phase, before anything is
applied to the cluster or benchmarked, so no goodput
value in this dataset is affected, but each pair consumes two iterations
of the fixed ten-iteration budget without the decision stage's choice for
those iterations ever being evaluated.


% ----- §6.3 Practical Implications -----
\section{Practical Implications}
\label{sec:discussion-implications}

\paragraph{For agentic software optimisation.} The clearest transferable
result is the code/deployment division of labour itself
(Section~\ref{sec:results-rq3}): when an agent can act on two levers that
address different failure classes, keeping them mutually exclusive per
step (Section~\ref{sec:methods-workflow}) is what makes it possible to
attribute a measured change to a cause at all, and this thesis's data
suggests the two levers really do specialise in practice, not just by
construction. Systems that let an agent freely mix implementation and
configuration changes in one step should expect the attribution problem
Section~\ref{sec:results-case-studies}'s backfire case illustrates \emph{within} a
single lever, only worse.

\paragraph{For Kubernetes deployment optimisation.} The
\textsc{ClickCount} evidence (Section~\ref{sec:results-case-studies}), reproduced
qualitatively by two different models on the same scenario, is more than a
single existence proof that an LLM agent, given only a schema and raw
load-test feedback, can rediscover a standard scaling heuristic (favour
horizontal fan-out over per-pod headroom for CPU-light, network-bound
workloads) without being told it. That is a meaningfully lower bar than
fully autonomous production capacity planning, but it is a higher bar than
today's reactive autoscalers (Section~\ref{sec:rw-cluster}) clear, since
HPA/VPA-style mechanisms do not reason about database topology or
placement at all.

\paragraph{For LLM-guided performance tuning more broadly.} The
code-correctness result above cautions against evaluating a
performance-tuning agent on its tuning behaviour alone. A benchmark that
hands such an agent a known-good application and scores only its
configuration choices would be measuring the smaller of the two effects
observed here, and would be structurally unable to see the class of bug
that surfaces only under load behind real infrastructure
(Section~\ref{sec:results-case-studies}).
